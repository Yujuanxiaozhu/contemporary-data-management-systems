# 基于 MongoDB 的问卷系统第一阶段项目完成报告

## 一、项目目标

本项目要求使用 MongoDB 开发一个简化的在线问卷系统，实现类似问卷平台的基本功能。用户注册并登录后可以创建和管理自己的问卷，设置不同类型的题目以及填写规则，并通过公开链接将问卷分享给其他用户填写。问卷提交后，创建者可以查看对应的统计结果。

第一阶段主要完成系统的基础设计和实现，并为之后第二阶段的需求修改保留扩展空间。因此在开发时不仅考虑了当前功能是否能够运行，也尽量避免将题目校验、跳转等规则直接写死在代码中。

本阶段最终实现了用户账户、问卷管理、四种内部题型、答案校验、条件跳转、公开填写、问卷提交、历史版本保存以及统计等功能。整个项目使用 MongoDB 存储数据，没有使用关系数据库，也没有使用现成的问卷系统框架。

## 二、系统设计

后端采用 Python 和 FastAPI 实现，数据库使用 MongoDB。前端没有采用 React、Vue 等复杂框架，而是使用 Jinja2、HTML、CSS 和少量原生 JavaScript，实现课程项目需要的管理和填写页面。

项目在代码结构上进行了分层。

Router 主要负责接收 HTTP 请求、检查登录状态和调用业务逻辑；Service 层负责题目管理、答案校验、跳转、版本保存、问卷提交和统计等主要业务；Schema 负责接口数据结构和类型检查；Core 模块负责环境配置、MongoDB 连接、密码处理和登录会话。

用户可以通过网页完成注册、登录、创建问卷、编辑题目、设置跳转规则、发布问卷、复制填写链接、填写问卷、查看统计以及关闭问卷等操作。

这种结构使不同功能之间相对独立，第二阶段如果出现新的需求，可以在现有模块上继续修改，而不需要重新实现整个系统。

## 三、MongoDB 数据库设计

项目目前主要使用以下集合：

- `users`：保存用户账号、密码哈希和注册时间等信息。
- `surveys`：保存当前问卷，包括基本信息、题目、跳转规则和当前结构版本。
- `responses`：保存用户提交的每一份答卷。
- `survey_versions`：保存已经发布过的问卷历史结构。
- `sessions`：保存登录会话。

题目 `questions` 和跳转规则 `jump_rules` 直接嵌入问卷文档中。因为它们通常和一份问卷一起读取和修改，并且不会脱离问卷单独存在，所以采用嵌入方式更加符合实际使用情况。

答卷没有嵌入问卷，而是单独存放在 `responses` 集合中。问卷可能产生大量填写记录，如果把所有答卷都放入同一个问卷文档中，文档会不断增大，也不方便独立查询和统计。

系统还建立了用户名、公开问卷 token、问卷版本等唯一索引，以及 owner、survey 和 response 查询所需要的索引。系统中的时间统一采用 UTC，MongoDB 的 ObjectId 在 API 返回时也进行了相应转换。

## 四、题目与校验设计

系统在内部将题目分为四种类型：

- 单选题 `single_choice`
- 多选题 `multiple_choice`
- 文本填空题 `text`
- 数字填空题 `number`

单选题和多选题可以配置选项，多选题可以限制最少、最多或固定选择数量。文本题可以限制最小和最大输入长度，数字题可以限制数值范围以及是否必须为整数。

项目将题目定义检查和用户答案检查统一放在 Validation Engine 中处理，而不是分别写在每个接口中。

例如，多选题会检查用户选择的选项是否真实存在、是否重复选择以及选择数量是否符合要求；数字题会检查范围、整数要求，同时排除布尔值、NaN 和 Infinity 等不合理数据。

必答题没有填写时会返回错误；非必答题可以不填写，但是一旦填写，答案本身仍然需要满足对应规则。

这样做的好处是创建题目和提交答卷时可以复用同一套规则，避免不同接口对相同题目的判断标准不一致。

## 五、条件跳转设计

问卷支持根据用户回答跳转到后面的指定题目。

跳转规则保存在问卷的 `jump_rules` 中，每条规则记录来源题目、判断方式、判断值、目标题目和优先级。例如单选题可以根据选择的选项跳转，多选题可以判断是否包含某个选项，数字题可以根据大于、小于或等于等条件进行跳转。

同一道题存在多条跳转规则时，系统按照优先级依次判断，第一条满足条件的规则生效。如果没有规则满足条件，则按照正常题目顺序进入下一题。

第一阶段只允许向后跳转，从设计上避免产生循环。同时 Jump Engine 在执行时仍保留了访问记录和最大执行步数检查，防止异常数据造成死循环。

在最终提交问卷时，服务器会根据实际答案重新计算用户应该经过的题目路径。因为跳转而被跳过的必答题不会要求回答，同时客户端也不能额外提交本来没有经过的题目答案。

## 六、问卷版本设计

问卷发布后仍然可能被修改。如果直接使用修改后的题目解释旧答卷，就可能出现旧选项已经不存在或者题型已经改变的问题。

因此系统增加了 `schema_version` 和 `survey_versions`。

问卷发布时会保存当时的题目和跳转规则。发布后的问卷如果发生结构变化，会产生新的版本，并保存新的历史结构。

每一份答卷都会记录自己填写时对应的问卷版本。之后读取或者统计旧答卷时，系统根据这个版本找到当时真实的问卷结构，而不是直接使用当前最新版问卷。

这样可以在保留历史填写数据的同时继续修改问卷，也为第二阶段需求变化留下了扩展空间。

## 七、填写与提交设计

公开问卷通过唯一的公开链接访问。

系统在填写和提交过程中检查问卷状态、截止时间、匿名设置、答案是否合法以及实际跳转路径。

如果问卷允许匿名填写，未登录用户也可以提交，答卷中的用户 ID 为空。如果不允许匿名，则必须登录后才能填写。

对于登录用户，如果问卷禁止重复填写，系统会通过数据库唯一约束避免同一个用户并发提交两份答卷。如果问卷允许多次填写，则可以保存多份记录。

由于匿名用户没有稳定的身份标识，系统没有强行声称可以准确判断两个匿名提交是否来自同一个人，这一点作为当前系统的限制保留。

## 八、统计设计

统计数据直接根据已经保存的 `responses` 动态计算，没有额外维护容易和实际答卷不一致的永久统计计数。

单选题统计每个选项被选择的人数以及回答人数；多选题统计回答人数、总选择次数和每个选项的选择次数；文本题保存并显示实际填写内容；数字题统计回答人数、原始数值、平均值、最小值和最大值。

由于问卷发布后可以修改，同一个题目在不同版本中可能出现不同选项甚至不同题型，因此统计时不会强行把不同版本的数据混在一起。

系统根据每份答卷记录的 `survey_schema_version` 读取对应的历史问卷结构，再分别计算各个版本的统计结果。被跳过或者没有回答的题目不会被计入该题的回答人数。

## 九、AI 使用过程

本项目开发过程中主要使用 Codex 辅助完成代码实现、测试和文档整理。

整个开发分为四轮逐步完成。第一轮主要建立项目结构、用户认证和基础问卷管理；第二轮实现题目模型、答案校验和版本控制；第三轮完成历史版本、条件跳转、公开填写和答卷提交；第四轮完成统计和管理页面。

每一轮使用的完整提示词、AI 实际创建或修改的文件、测试结果、出现的问题以及修正过程都记录在 `docs/ai-log.md` 中。

AI 主要负责根据确定的设计实现代码、补充测试以及发现部分边界情况。实际开发过程中并没有直接接受所有生成结果，而是通过自动测试、真实 MongoDB 测试和实际启动检查不断验证。

例如开发过程中曾出现启动探测超时，也通过故障注入测试过历史版本保存失败的情况。相关错误信息和处理过程都保留在对应的迭代记录中，没有为了报告内容另外编造错误或人工修改记录。

## 十一、开发中遇到的问题及解决方法

### 1. 问卷修改后旧答卷难以解释

最开始只有 `schema_version` 数字，如果没有保存对应版本的题目结构，那么之后仍然无法知道旧答卷填写时的真实问卷内容。

因此增加了 `survey_versions` 集合，在问卷发布和发布后发生结构变化时保存对应的历史结构。答卷通过 `survey_id + survey_schema_version` 与历史结构关联。

### 2. 发布后修改可能造成版本不一致

如果先修改当前版本，再保存历史结构，中间发生数据库错误，就可能出现当前版本已经变化但历史快照不存在的情况。

因此实现时对版本切换过程进行了控制。只有对应历史结构成功保存后才完成当前版本切换，并对并发修改返回冲突错误。

### 3. 跳转后的必答题处理

如果用户从第 1 题直接跳到第 5 题，第 2～4 题即使被设置为必答，也不能要求用户回答。

因此正式提交时不直接遍历所有题目检查 required，而是由 Jump Engine 根据实际答案重新计算用户应该经过的路径，只检查实际路径中的必答题。

### 4. 重复提交的并发问题

如果只采用“先查询是否存在，再插入”的方式，两个并发请求可能同时查询到不存在记录，然后同时成功提交。

因此对于禁止重复填写的登录用户，系统生成唯一去重键，并利用 MongoDB 唯一索引作为最终限制，使并发请求中只有一个可以成功保存。

### 5. 历史版本统计问题

不同版本中同一个题目可能增加选项或改变题型，如果直接合并统计会产生不正确的结果。

因此统计时按照 `schema_version` 分组，并使用对应版本的历史结构计算，不强行合并含义已经不同的数据。

## 十二、尚存限制

当前系统面向课程项目规模，没有进行大规模压力测试，也没有实现复杂图表、统计分页或大型前端框架。

项目没有使用真实浏览器自动点击工具进行完整 E2E 测试，而是使用 TestClient、真实 HTTP/Uvicorn 流程、JavaScript 语法检查以及实际 MongoDB 测试完成验证。

匿名填写无法可靠识别同一个自然人，因此无法完全限制匿名用户重复提交。允许多次提交的情况下也没有实现通用网络请求幂等机制。

历史版本数据的不可修改主要通过程序业务逻辑控制，因此实际部署时 MongoDB 不应直接向不可信用户开放写权限。

这些限制不影响当前课程要求的主要功能，但如果以后继续扩展为实际在线系统，还可以进一步完善。

## 十三、第一阶段总结

第一阶段已经完成问卷系统要求的主要功能，包括用户管理、问卷管理、多种题型、输入校验、条件跳转、公开填写、答卷保存以及结果统计。

开发过程中使用 MongoDB 的嵌入文档和独立集合组织不同性质的数据，并通过历史版本保存解决问卷修改后的旧数据兼容问题。

目前代码、测试和文档均保留在同一项目中。第二阶段收到新的需求后，将继续在本阶段代码基础上修改和扩展，不重新设计一个完全独立的新系统。
