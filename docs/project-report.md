# 基于 MongoDB 的问卷系统项目报告

## 一、项目背景与第一阶段

这个课程项目要求用 MongoDB 写一个简化的在线问卷系统：用户注册登录后可以创建问卷、设置题目和跳转规则，把公开链接发给别人填写，再查看统计结果。整个项目没有使用关系数据库，也没有套用现成的问卷平台。

第一阶段完成了账户、问卷管理、四种题型、答案校验、条件跳转、公开填写和按问卷查看统计。后端是 FastAPI，数据存在 MongoDB，前端用 Jinja2、HTML 和少量原生 JavaScript。第一阶段结束时，一份问卷把自己的题目直接存在问卷文档里，每道题只有一个问卷内的局部 ID。

## 二、第二阶段的需求变化

第二阶段要求在原来的代码上继续修改，而不是另写一套系统。新增的要求主要是：

- 题目要能在多个问卷里复用；
- 题目要有稳定的全局身份和不可变的版本；
- 问卷要固定使用某个确定的题目版本；
- 发布以后问卷的题目和跳转结构不能再改；
- 需要修改时，从历史快照创建一份独立的修订问卷；
- 题目可以按版本分享，也要能撤销；
- 增加私人题库，用来组织自己可用的题目；
- 记录题目在本人问卷中的使用情况；
- 按题目做跨问卷统计，但只看本人的问卷。

这些要求放在一起，实际上改变了第一阶段“题目属于某份问卷”的组织方式：题目必须变成独立对象，问卷只引用它。

## 三、第一阶段模型为什么不够用

第一阶段把题目嵌在问卷里，看起来简单，但一旦要复用题目就遇到问题。同一道题出现在两份问卷中时，每份问卷只知道自己内部的局部 ID，系统没有依据判断它们是不是同一个题。直接按题名或相似内容去合并并不可靠，题干稍有修改或者重名都会出错。

另外，第一阶段修改问卷就是直接改当前结构。已发布的问卷被改掉以后，旧答卷找不到当时对应的题目定义，统计也只能按问卷做，无法按题目汇总。分享也没有版本概念，无法只授权某个确定版本。

所以第二阶段先把题目身份单独建立起来，并且规定定义只新增、不覆盖。

## 四、全局题目身份与不可变版本

`questions` 集合表示题目族，持有稳定的全局 ID 和所有者；`question_versions` 保存具体定义。每次修改题目都创建新的 `version_no`，旧版本保持原样。恢复旧版本不是把旧记录改回来，而是根据旧版内容再生成一个新版本，因此历史链条始终完整。派生版本记录 `derived_from_version_id`，表示它来自哪个被授权的版本。

创建、改版、恢复和派生都写 `stage2_operations` 操作记录，请求带幂等键。相同键重复提交不会产生第二个版本；如果上一次执行中断，可以读取操作状态并按原意图恢复。

题目族和版本分开以后，题意发生实质变化时可以新建题目族，而只是措辞修订时可以在同一个族里加版本。这个判断交给用户，系统不自动按文本相似度合并。

## 五、固定绑定与发布快照

问卷中的每个题目位置有一条绑定，记录 `local_question_id`、全局 `question_id`、确定的 `question_version_id`，以及该位置自己的必答设置。局部 ID 仍然用于答卷、跳转和页面定位，但它只在本问卷内有意义，不当作跨问卷身份。必答覆盖只影响这个位置，不会改动全局版本。

发布时系统把当前题目、跳转规则和绑定写入 `survey_versions`，形成快照。问卷进入 published 或 closed 后，题目和跳转结构只读。每份答卷都记录填写时的 `survey_schema_version`；查看历史答卷或统计时读对应快照，而不是用现在的问卷去解释旧数据。

需要修改已发布问卷时，`revisions.py` 从指定的历史快照创建一份新的问卷草稿，分配新的问卷 ID 和公开链接，原问卷、旧链接和已有答卷都不受影响。修订创建也使用操作记录，中断后可能留下待恢复状态；这里依靠条件更新和唯一索引，不把多个集合的写入说成事务。

## 六、版本分享与撤销

题目所有者可以把某个确定版本分享给指定用户。接收者可以在自己的草稿里绑定该版本，也可以从它派生出一份自己的题目，但不能修改原题，也不能把原题再分享给别人。分享记录按“版本 + 接收者”唯一，并带授权代次，发布时把准入与本次确定内容绑定。

撤销分享后，新的绑定和新的发布都会被拒绝。已经发布并冻结的快照不受影响，仍然按当时的授权解释。草稿里已经失效的引用不会被系统悄悄删掉，页面会提示移除、替换或重新授权。这样不会因为一次撤销把用户正在编辑的内容改得面目全非。

## 七、私人题库

`question_banks` 和 `bank_items` 实现私人题库。题库只是本人组织题目的入口，不代表题目所有权。每个成员记录一个明确的默认版本，修改默认值只影响以后往问卷里选题，不会自动升级已经建好的问卷。成员如果指向已经被撤销的共享版本，记录保留但标记为不可用。

题库行为本身不会写问卷历史，也不会因为删除题库而删掉题目、版本或已有答卷。

## 八、使用追踪：生成、重建与完整性

`question_usages` 是一个可以从权威数据重建的索引，不是新的真实来源。它把本人草稿中的绑定和本人已发布快照投影成“某个问卷的某个位置使用了某个题目版本”的记录。重建时不会从题库成员反推问卷，也不按题名猜测。

重建流程先写 `usage_generations` 的新代次，状态为 BUILDING；`usage_manifests` 逐个来源记录摘要和预期行数；全部写完后核对数量和摘要，再切到 READY，并由 `usage_heads` 指向这个活动代次。查询时会重新检查来源、行数、摘要和权限，只要代次不完整、来源发生变化或者旧数据缺少映射，就返回 409，而不是返回一部分结果。

重建是维护操作，不提供普通 HTTP 接口。命令 `scripts/rebuild_question_usages.py` 必须显式给出 URI、数据库名、owner ID 和 `--apply`，不会从默认配置里挑库。重建只写派生索引，不修改问卷快照和答卷。

## 九、跨问卷统计

跨问卷统计先使用通过完整性检查的 usage，确定本人在哪些问卷、哪些位置用过这个题目，然后按答卷自己的 schema 版本读取对应快照，用其中的局部题目定义和答案做统计。

统计按 `question_version_id` 分组，不同版本不合并。同一版本在同一份问卷的两个位置分别计数，因为它们是两个作答位置；不同问卷恰好用了相同局部 ID 也不会被当成同一个位置。单选返回各选项次数和占有效回答的百分比；多选另外返回总选择次数；数字返回数量、最小值、最大值和平均值，没有有效答案时后三项为 null；文本返回有效回答内容。

这里统计单位是“有效回答次数”。匿名的或者重复的提交无法可靠对应到不同自然人，所以不把它说成人数。题目被分享出去，不代表原题所有者能看接收者的问卷或答卷；统计范围始终是当前用户自己的问卷。

## 十、校验、跳转与旧数据兼容

题目和答案仍然经过统一校验模块：选项必须属于该题，数字不能是布尔值或非有限值，必答只在路径实际访问到该题时检查。跳转规则只允许向前的路径，提交时服务端重新计算访问路径，因此被跳过的必答题不要求填写。

旧数据方面采取保守策略。旧快照和旧答卷不重写；没有可信映射的旧位置不会按题名、局部 ID 或内容相似度归到新题目，而是直接报错（`legacy_mapping_required`）。U11 只允许在明确修订某份旧快照时，逐个位置做显式转换，不能推出一个全库自动迁移。

在隔离的旧样本上做过只读盘点和故障恢复演练：两个没有映射的位置返回 409；注入中断后留下一个 PREPARED 操作和一个已提交的题目版本，重试后两个位置完成映射，而且原旧快照没有变化。这些都在临时 UUID 数据库里进行，业务数据库没有执行迁移。

## 十一、测试和验证

最终功能代码上做过一次完整回归，共 846 个节点，结果是 810 passed、36 failed，退出码 1。和进入 Slice 7 之前的 831 个节点逐项比较，原有节点的通过/失败状态没有变化，新增的 15 项全部通过，没有新增失败。

这 36 项不是第二阶段引入的回归，而是第一阶段测试与第二阶段正式语义之间的冲突：其中 28 项仍然按第一阶段的做法要求修改已经发布的结构，8 项依赖旧的题目存储或绑定断言。第二阶段明确要求冻结结构和固定版本，所以没有为了追求全绿把旧行为改回去，也没有删除、跳过或标记这些断言。

最终集成阶段在随机 UUID 数据库上启动了真实的 MongoDB 和 Uvicorn，走通了题目版本、草稿绑定、发布快照、分享、撤销、私人题库选题、答卷、usage 重建和本人统计的版本分组，并验证了跨用户权限隔离。旧数据的只读盘点和恢复演练同样在隔离库里完成。最终集成只改文档和验证脚本，没有改业务代码。

开发过程中也遇到过实际问题。一次是浏览器从后退缓存返回页面时按钮保持禁用；另一次是 Slice 4 的完整回归中，新加的所有权检查绕过了原有调用边界，导致一项本来通过的旧测试失败。这两处都定位并修正了，过程记录保留在阶段二目录，没有删掉失败的痕迹。

## 十二、已知限制

- usage 和统计是动态视图，查询时会复核来源和权限，但不提供跨集合的事务快照。
- 没有做真实进程强杀、断网未知确认和大规模压力测试；性能和 BSON 大文档边界还没有专门验证。
- 如果一份旧快照和它的所有引用都已经消失，现有数据无法证明它曾经存在。
- 匿名或允许重复填写的问卷，无法可靠计算独立人数。
- 完整回归里仍有 36 项历史断言失败，没有清理。
- 撤销分享后，仅凭本人历史绑定继续访问原共享题的窄权限还没有批准，因此没有实现。

## 十三、AI 使用说明

这个项目的代码、测试和文档大量使用了 Codex 生成和修改，期间 ChatGPT 对各个切片的材料做过独立只读复审。产品语义由我确定，包括发布后冻结、分享按确定版本、统计只看本人问卷，以及撤销前已经获准的操作可以完成。

AI 的输出没有被默认当成正确。上面提到的浏览器返回问题和 Slice 4 的测试回归，都是通过实际测试或复审发现后修正的。完整的第一阶段提示与操作记录在 [AI 使用日志](ai-log.md)，第二阶段过程在 [阶段二 AI 日志](stage2/ai-log.md)。

## 十四、总结

第二阶段没有推翻第一阶段的问卷、校验、跳转和提交流程，而是在它上面把题目身份独立出来，再用不可变版本、固定绑定和发布快照把历史数据固定住。分享、题库、usage 和跨问卷统计都建立在明确的版本和权限之上，遇到旧数据缺少证据时选择报错而不是猜测。

系统仍然是一个课程规模的项目：没有分布式事务，也没有做压力测试。已知的 36 项旧测试冲突和尚未覆盖的故障场景都在测试文档里如实说明，没有为了让结果好看而修改断言或隐藏限制。
